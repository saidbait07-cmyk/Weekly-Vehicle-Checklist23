# SVIFMS — الغالبي | نظام فحص المركبات وإدارة الأسطول

تطبيق Next.js فعلي بخادم Node.js وقاعدة PostgreSQL، يختلف عن العرض الثابت القديم في `index.html`. قاعدة البيانات هي مصدر الحقيقة، وتتحقق واجهات API من الجلسة والدور والتعيين قبل قراءة البيانات أو حفظها.

## التشغيل المحلي

يتطلب Node.js 22 أو أحدث، وPostgreSQL 16 (محلياً أو لدى Supabase/Neon).

```bash
npm ci
cp .env.example .env
```

عدّل `.env`: ضع رابط قاعدة البيانات في `DATABASE_URL`، وكلمة مرور أولية فريدة في `SEED_ADMIN_PASSWORD` (12–72 بايت). لا ترفع هذا الملف إلى GitHub.

لتشغيل PostgreSQL محلياً باستخدام Docker، ضع `POSTGRES_PASSWORD` في بيئة الطرفية أو في `.env`، ثم نفّذ:

```bash
docker compose up -d db
```

يجب أن تتطابق كلمة المرور في `DATABASE_URL` مع `POSTGRES_PASSWORD`. مثال محلي: `postgresql://svifms:YOUR_PASSWORD@localhost:5432/svifms?schema=public`.

```bash
npm run db:migrate
npm run db:seed
npm run dev
```

افتح `http://localhost:3000`. الحساب الأول `ADMIN001` (أو `SEED_ADMIN_ID`)، وكلمة مروره هي التي اخترتها. يفرض النظام تغييرها عند أول دخول، ويلغي الجلسات القديمة عند تغيير كلمة المرور.

التهيئة قابلة للتكرار: لا تعيد تعيين كلمات مرور الحسابات الموجودة، ولا تعدل نسخ قوائم الفحص المنشورة. `SEED_DEMO=true` ينشئ مركبة تجريبية واحدة، ولا ينشئ سائقين بكلمات مرور مشتركة.

## أول دورة استخدام

1. سجّل دخول المدير وغيّر كلمة المرور، ثم سجّل الدخول مجدداً.
2. من الإدارة: أضف سائقاً ومشرفاً مع كلمات مرور مؤقتة، وأضف مركبة.
3. عيّن السائق للمركبة في تاريخ العمل بتوقيت مسقط، وعيّن المشرف للمركبة. إعادة التعيين تحفظ السجل السابق.
4. يسجّل السائق الدخول، ويغيّر كلمة مروره، ويختار المركبة المعيّنة له اليوم.
5. يملأ البنود 1–27، والعداد وبيانات السائق والتوقيع المكتوب وانتهاء الرخصة ووصف العطل والإجراء. البنود 28–32 حقول بيانات واعتماد، وليست أسئلة نجاح/فشل.
6. الفشل ينشئ بلاغ عطل تلقائياً، والفشل الحرج يغيّر حالة سلامة المركبة ويرسل إشعاراً للمشرف. التكرار خلال سبعة أيام ينشئ إشعاراً إضافياً.
7. يتابع المشرف البلاغ: إقرار، مراجعة أو صيانة، حل، ثم تحقق وإغلاق. يمكن تسجيل الفني والعمل والتكلفة وإرفاق صور، واعتماد الفحص بتوقيع مكتوب مسجل باسم المستخدم في سجل التدقيق.
8. يستطيع المدير والمشرف تصدير ملف Excel ضمن نطاقهما.

## الوظائف المنفذة

- 24 جدولاً في Prisma، وترحيل SQL كامل ينشئ الجداول والعلاقات والفهارس.
- جلسات عشوائية مخزنة بصيغة SHA-256 في قاعدة البيانات وCookie من نوع HttpOnly؛ كلمات المرور مشفرة باستخدام bcrypt. انتهاء الجلسة بعد 8 ساعات.
- قفل مؤقت لمدة 15 دقيقة بعد خمس محاولات فاشلة لحساب موجود؛ حماية طلبات التعديل بفحص Origin.
- صلاحيات ADMIN / SUPERVISOR / DRIVER على الخادم، دون الاعتماد على دور يرسله المتصفح. نطاق السائق من تعيين اليوم، ونطاق المشرف من تعييناته الفعالة.
- إنشاء الموظفين والمركبات والتعيينات من الواجهة، وAPI لتعطيل الحساب أو إعادة تعيين كلمة مرور مؤقتة مع إلغاء جميع جلساته.
- 27 بند فحص بالعربية والإنجليزية مطابق لترتيب الاستمارة، مع حقول البيانات 28–32. التوقيع المكتوب ليس توقيعاً رقمياً بشهادة تشفير.
- حفظ الفحص والإجابات والأعطال والعداد والتدقيق داخل معاملة Serializable واحدة. يمنع تكرار فحص المركبة والسائق في اليوم، وتُعاد نتيجة الطلب نفسه عند تكرار مفتاحه.
- فهرس جزئي يضمن سائقاً فعالاً واحداً لكل مركبة وتاريخ، ويسمح بسجلات تعيين سابقة متعددة.
- Trigger يمنع UPDATE وDELETE وTRUNCATE على سجل التدقيق. مالك قاعدة البيانات بصلاحيات DDL يستطيع تغيير الـ Trigger؛ استخدم حساب تشغيل محدوداً في الإنتاج.
- إنشاء QR خاص بالمركبة وفتحها بالرابط، مع تطبيق الصلاحيات عند حل الرمز. لا توجد كاميرا ماسح مدمجة؛ يمكن استخدام قارئ الهاتف.
- صور JPG/PNG/WebP حتى 5 MB، مع التحقق من ترويسة الملف وتقديمه من API محمي، وليس من مجلد عام.
- Excel بعشر أوراق حقيقية: المركبات، الفحوصات، الإجابات، الأعطال، الصيانة، التعيينات، الموظفون، بيانات القائمة الأسبوعية، التدقيق، والإشعارات. سجل التدقيق للمشرف يقتصر على عملياته الشخصية. الفحوصات والأعطال محدودة إلى 10,000 سجل لكل تصدير.
- Manifest وService Worker لتخزين غلاف التطبيق وملفاته، دون تخزين API أو صور الأعطال في Cache Storage. بعد تحميل التطبيق بنجاح يمكن للتبويب المفتوح استعادة بيانات جلسة العرض من sessionStorage والعمل دون شبكة.
- فحوصات عدم الاتصال تُحفظ في طابور localStorage خاص بحساب المستخدم على الجهاز. المزامنة تتم بزر صريح بعد الاتصال وتسجيل الدخول، مع إعادة التحقق من جميع القيود في الخادم. فحص يوم سابق يُرفض للمراجعة ولا يُنقل تلقائياً لتاريخ جديد. لا توجد مزامنة خلفية أو اعتماد للفحوصات المتأخرة.

## حدود النطاق الحالية

واجهة التشغيل الجديدة عربية مع أسماء بنود إنجليزية، وليست ترجمة كاملة للهندية والأردية. العرض القديم مستقل ولا يتصل بقاعدة البيانات. إدارة نسخ قوالب الفحص والترجمات والنسخ الاحتياطي المجدول واسترجاعه ليست لها واجهات تشغيل في هذه النسخة؛ وجود جداولها لا يعني تنفيذ هذه الوظائف. لا توجد خدمة بريد/SMS أو تخزين صور سحابي مهيأة تلقائياً. الإشعارات متاحة عبر API وتظهر في لوحة التحكم.

## النشر

GitHub Pages يعرض النسخة الثابتة فقط، ولا يشغّل هذا الخادم. انشر المشروع على استضافة Node.js أو Vercel، واربطه بقاعدة PostgreSQL مستقلة. خطوات الإصدار:

```bash
npm ci
npm run db:migrate
npm run build
npm start
```

نفّذ التهيئة مرة واحدة بمتغيرات حساب المدير المختارة، ثم احذف كلمة المرور الأولية من إعدادات التشغيل. استخدم HTTPS؛ Cookies تكون Secure في وضع production. استخدم اتصال TLS لقاعدة البيانات لدى مزودك، ورابط اتصال مباشر للترحيلات إذا تطلبه المزود. التطبيق لا يحتاج أسراراً في متغيرات `NEXT_PUBLIC_*`.

الصور تخزن في `UPLOAD_DIR` (الافتراضي `./uploads`). يلزم قرص دائم قابل للكتابة ومشترك عند تشغيل عدة نسخ. استضافات serverless ذات الأقراص المؤقتة تحتاج محول تخزين دائم قبل استخدام الصور في الإنتاج. لا تضع `uploads` داخل `public`. خذ نسخاً احتياطية من PostgreSQL ومجلد الصور وفق سياسة مؤسستك.

ملف GitHub Pages صار يدوياً فقط، ويرفع `public/` بدلاً من المستودع كاملاً. للنشر الكامل استخدم استضافة الخادم، وليس هذا الـ Workflow.

## API مختصر

كل المسارات تحت `/api`. التعديل يحتاج Cookie جلسة وOrigin مطابقاً للموقع.

| المسار | الطريقة | الاستخدام |
|---|---|---|
| `/auth/login`, `/auth/logout`, `/auth/password` | POST | الجلسات وكلمة المرور |
| `/auth/me` | GET | هوية الجلسة دون أسرار |
| `/vehicles`, `/users` | GET / POST | المركبات والموظفون |
| `/users/:id` | PATCH | `status` أو `temporaryPassword`، للمدير |
| `/assignments` | POST | تعيين سائق أو مشرف، للمدير |
| `/checklist` | GET | النسخة المنشورة وبنودها |
| `/qr?token=...` | GET | حل الرمز داخل نطاق المستخدم |
| `/inspections` | GET / POST | قراءة الفحوصات وإرسال فحص |
| `/inspections/:id` | PATCH | `supervisorSign` للمشرف أو المدير |
| `/faults` | GET | الأعطال ضمن النطاق |
| `/faults/:id` | PATCH | الحالة التالية وملاحظات الإجراء |
| `/faults/:id/photos` | POST | multipart بحقل `file` |
| `/photos/:id` | GET | الصورة المحمية |
| `/maintenance` | POST | تسجيل أعمال الصيانة |
| `/notifications` | GET | إشعارات المستخدم |
| `/audit` | GET | آخر 200 عملية، للمدير |
| `/export` | GET | ملف XLSX ضمن نطاق المدير أو المشرف |

English: This repository includes a working Next.js/PostgreSQL fleet inspection application with server-side sessions, role and vehicle scoping, dated assignments, atomic inspections, fault workflows, maintenance, protected image uploads, supervisor signoff, audit immutability, QR links and scoped Excel exports. The original static demo is retained separately. See the explicit scope and hosting notes above; no external deployment or cloud database is created automatically.


## نشر النظام الكامل على Render

أضيف ملف `render.yaml` لنشر الخادم وقاعدة PostgreSQL وقرص دائم للصور معاً. لا توجد موارد سحابية منشأة بمجرد وجود هذا الملف. الخطة المقترحة تستخدم موارد مدفوعة؛ راجع السعر الذي تعرضه Render قبل الموافقة.

1. ارفع محتويات هذا المجلد (بما فيها الملفات المخفية، دون `.env` أو `node_modules` أو `uploads`) إلى مستودع GitHub.
2. في حساب Render اختر **New → Blueprint** واربط المستودع والفرع المطلوبين.
3. سيقرأ Render ملف `render.yaml`. أدخل كلمة مرور أولية فريدة في حقل `SEED_ADMIN_PASSWORD` داخل Render فقط، ثم راجع التكلفة ووافق على الإنشاء.
4. ينشئ Blueprint قاعدة البيانات والخادم والقرص. يتصل الخادم بالقاعدة تلقائياً، ويطبق الترحيلات وينشئ حساب المدير أثناء أول إصدار.
5. انتظر حالة **Live** ثم افتح رابط الخدمة الذي يعرضه Render (عادة ينتهي بـ `.onrender.com`). لا يُعرف الرابط النهائي قبل إنشاء الخدمة.
6. سجل الدخول باسم `ADMIN001` وكلمة المرور التي أدخلتها، وغيّرها فوراً. بعد نجاح التهيئة، يمكنك حذف متغير كلمة المرور الأولية، لكن غيّر `preDeployCommand` إلى `npm run db:migrate` أولاً حتى لا تتطلب الإصدارات التالية تشغيل التهيئة.

يفحص `/api/health` اتصال PostgreSQL ويرجع حالة عامة دون تفاصيل الاتصال. الصور تُحفظ في `/var/data/uploads` على قرص دائم، واتصالات قاعدة البيانات الخارجية محجوبة افتراضياً. النشر التلقائي عند كل دفع معطل؛ النشر اللاحق يتم من Render. يلزم إعداد النسخ الاحتياطي والاستعادة وفق سياسات المؤسسة.
